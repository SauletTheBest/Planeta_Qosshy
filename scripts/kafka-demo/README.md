# Kafka в Planeta Qosshy: как это устроено и как пощупать руками

## Что происходит, когда заказ оплачен

```text
 магазин (api)                                    Kafka                        notifier
 ─────────────                                    ─────                        ────────
 webhook банка «оплачено»                topic "shop.order-events"         читает события,
   │  ОДНА транзакция:                   ┌─ партиция 0 ─┐                  шлёт письмо:
   ├─ orders.status = paid               ├─ партиция 1 ─┤  ──────────►     «оплачен», «отправлен»,
   ├─ order_events  (история заказа)     ├─ партиция 2 ─┘   группа         «доставлен», «отменён»,
   └─ outbox_events (событие к отправке)        ▲           "notifier"      «деньги возвращены»
         │                                      │                                │
         └── relay (раз в секунду) ─────────────┘                          Mailpit / SMTP
             берёт неотправленные, публикует,
             ставит published_at
```

| Где в коде | Что делает |
|---|---|
| `events/events.go` | **Контракт**: структура события. Её читают и магазин, и notifier |
| `shop/admin.go` → `addEvent` | Каждая строка истории заказа сразу пишет событие в outbox (в той же транзакции) |
| `shop/publish.go` | Собирает событие: покупатель, товары, сумма, новый статус |
| `outbox/outbox.go` | `Enqueue` (запись в таблицу), `PublishBatch` и `RunRelay` (отправка в Kafka) |
| `outbox/kafka.go` | Настройки «писателя» Kafka: ключ → партиция, `RequireAll` |
| `notify/notify.go` | Какое письмо на какое событие; защита от дублей |
| `cmd/notifier/main.go` | Отдельная программа: читает Kafka как группа `notifier` |
| `migrations/000009_outbox.*.sql` | Таблицы `outbox_events` и `notifier_processed_events` |

## Пять идей, ради которых всё это

### 1. Transactional outbox — «сначала в свой журнал, потом на почту»

Представь кассира. Он не бежит на почту отправлять чек сразу после продажи: вдруг почта
закрыта, а покупатель уже ушёл. Он записывает «отправить чек» в журнал **той же ручкой и в
ту же минуту**, что и саму продажу. Курьер раз в минуту смотрит в журнал и относит всё, что
не отмечено.

* Отправлять в Kafka прямо из обработчика нельзя: Kafka лежит → событие потеряно; транзакция
  откатилась **после** отправки → все узнали о том, чего не было.
* С outbox «заказ оплачен» и «есть событие об этом» — **одна** запись в базу. Kafka может
  лежать час: события подождут в таблице.

| Плюсы | Минусы |
|---|---|
| Ничего не теряется и ничего лишнего не уходит | Задержка ~1 с (relay опрашивает таблицу) |
| Магазин работает, даже когда Kafka недоступна | Ещё одна таблица, которую надо чистить (сейчас она только растёт) |
| Всё видно SQL-запросом: что не ушло и почему (`last_error`) | Возможна **повторная** отправка (relay упал между «отправил» и «отметил») → получатели должны уметь отсекать дубли |

> В больших системах вместо опроса таблицы читают журнал изменений PostgreSQL (CDC,
> Debezium). Идея та же, задержка меньше, но это ещё один сервис.

### 2. Ключ сообщения = номер заказа → порядок

Топик поделён на 3 **партиции** — как 3 кассы в магазине. Kafka гарантирует порядок
**только внутри одной партиции**. Сообщения с одинаковым ключом всегда попадают в одну и ту
же партицию, поэтому «оплачен» всегда прочитают раньше, чем «отправлен». События **разных**
заказов идут параллельно в разных партициях.

### 3. Группа и смещение (offset) — закладка в книге

Kafka не удаляет сообщение после прочтения (как это делает обычная очередь). Она хранит его
7 дней (`retention.ms`), а для каждой **группы читателей** помнит **закладку** — до какого
места та дочитала. Поэтому:

* notifier выключен → сообщения копятся, «отставание» (**lag**) растёт;
* notifier включился → читает с закладки, ничего не пропускает;
* завтра появится сервис аналитики со своей группой → он прочитает **те же** события с начала,
  не мешая notifier.

### 4. «Хотя бы один раз» + идемпотентность

notifier сдвигает закладку (`CommitMessages`) **после** отправки письма. Упал между «отправил»
и «сдвинул» → после перезапуска прочитает это сообщение снова. Поэтому он помнит ID
обработанных событий (`notifier_processed_events`) и второй раз письмо не шлёт.

Обратный порядок («сначала сдвинуть, потом отправить») давал бы «не больше одного раза»:
без дублей, но с риском **потерять** письмо. Для уведомлений лишнее письмо — меньшее зло.

### 5. Событие несёт всё нужное

В событии уже есть email покупателя, товары и сумма. notifier **не ходит** в таблицы магазина
за подробностями — сервисы не зависят друг от друга. Минус: персональные данные (email) лежат
в Kafka 7 дней — в настоящем проекте это нужно учитывать (кто имеет доступ к топику).

## Посмотреть на своём стенде

```bash
cd Planeta_Qosshy
docker compose --profile dev up -d --build
```

* **kafka-ui** — <http://localhost:8085>
  * *Topics → shop.order-events → Messages* — сами события (JSON), ключ, партиция, offset;
  * *Consumers → notifier* — закладка по каждой партиции и **lag**.
* **Mailpit** — <http://localhost:8025> — письма покупателю.

Купи что-нибудь (карта `4242 4242 4242 4242`), потом в админке нажми «Отправлен» — и смотри,
как в kafka-ui появляются сообщения, а в Mailpit письма.

### Опыты (по одному, на своём стенде)

| Опыт | Команда | Что увидишь |
|---|---|---|
| Выключить notifier | `docker compose stop notifier`, потом сделать заказ | В kafka-ui у группы `notifier` lag 1, письма нет. `docker compose start notifier` → письмо пришло, lag 0 |
| Выключить Kafka | `docker compose stop kafka`, потом оплатить заказ | Магазин работает. В базе: `SELECT id, attempts, last_error FROM outbox_events WHERE published_at IS NULL;`. `docker compose start kafka` → строка отправится, придёт письмо |
| Перечитать всё заново | `docker compose stop notifier`, затем сброс закладки (ниже), затем `start` | notifier прочитает все события ещё раз, в логе `already handled`, **новых писем нет** |
| Логи notifier | `docker compose logs -f notifier` | Строка на каждое письмо |

Сброс закладки группы на начало топика (notifier должен быть остановлен):

```bash
MSYS_NO_PATHCONV=1 docker exec -e KAFKA_HEAP_OPTS=-Xmx96m planeta_qosshy_kafka \
  /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:29092 \
  --group notifier --topic shop.order-events --reset-offsets --to-earliest --execute
```

* `MSYS_NO_PATHCONV=1` — иначе Git Bash превратит `/opt/kafka/...` в `C:/Program Files/Git/opt/...`.
* `KAFKA_HEAP_OPTS=-Xmx96m` — утилиты Kafka тоже Java; без этого каждая возьмёт 256 МБ и
  будет толкаться с брокером за память контейнера.

## Автоматическая проверка: `e2e.sh`

```bash
bash scripts/kafka-demo/e2e.sh          # ~3–5 минут, 32 проверки
KEEP=1 bash scripts/kafka-demo/e2e.sh   # оставить копию, чтобы посмотреть в kafka-ui :18085
bash scripts/kafka-demo/e2e.sh down     # удалить оставленную копию
```

Скрипт поднимает **отдельную копию** стенда (проект `pq-kafka-e2e`, контейнеры `pq-e2e-*`,
свои volume и порты 18090/18081/18025/18085) — твой стенд и его база не трогаются. В конце
копия удаляется вместе со своими данными.

## Грабли, на которые мы уже наступили

| Симптом | Причина | Как исправлено |
|---|---|---|
| Контейнеры не могут писать в Kafka, хотя порт открыт | `KAFKA_ADVERTISED_LISTENERS: localhost:9092`: Kafka говорит клиенту «дальше ходи на localhost», а `localhost` в контейнере `api` — это сам `api` | Две «двери»: `INTERNAL://kafka:29092` для контейнеров, `EXTERNAL://localhost:9092` для Windows |
| `advertised.listeners cannot use the nonroutable meta-address 0.0.0.0` | Адрес контроллера Kafka берёт из `KAFKA_LISTENERS`, а `0.0.0.0` объявлять нельзя | `CONTROLLER://:9093` (пустой хост = все интерфейсы) |
| Данные Kafka пропадают при пересоздании контейнера | Образ `apache/kafka` пишет в `/tmp/kraft-combined-logs`, а volume был подключён к другой папке | `KAFKA_LOG_DIRS=/var/lib/kafka/data` |
| `password authentication failed` после повторного запуска | `POSTGRES_PASSWORD` действует **только** при первом создании volume | e2e.sh начинает с чистого листа (`down -v` своей копии) |
| Ошибка Kafka видна в `outbox_events` только через ~10 с | `kafka-go` по умолчанию повторяет отправку 10 раз | `MaxAttempts: 3`: долгие сбои — работа relay |
